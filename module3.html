1. SQL Basics

SQL (Structured Query Language) is the standard language for querying relational databases. Every SQL query follows a logical execution order that differs from the written order — understanding this is key to writing correct queries.

1.1 Logical Execution Order

SQL executes clauses in this order, regardless of how they are written:

StepClauseWhat it does
1FROM + JOINIdentify source tables and combine them
2WHEREFilter rows (before grouping)
3GROUP BYGroup remaining rows
4HAVINGFilter groups (after grouping)
5SELECTChoose and compute columns
6DISTINCTDeduplicate
7ORDER BYSort results
8LIMIT / OFFSETRestrict number of rows returned
Key Implication

Because WHERE runs before SELECT, you cannot reference a column alias defined in SELECT inside a WHERE clause. Use HAVING for filtering on aggregated values (computed after GROUP BY), or wrap the query in a subquery/CTE if you need to filter on a SELECT alias.

1.2 Basic Query Structure

SELECT  column1,
        column2,
        column3 * 1.18 AS price_with_gst    -- computed column with alias
FROM    orders
WHERE   order_date >= '2024-01-01'
  AND   status IN ('completed', 'shipped')
  AND   amount IS NOT NULL
ORDER BY order_date DESC
LIMIT   100;

2. Aggregate Functions & GROUP BY

Aggregate functions collapse multiple rows into a single summary value. They are always used with GROUP BY (unless applied to the entire table as one group).

2.1 Core Aggregate Functions

FunctionDescriptionNULL handling
COUNT(*)Count all rows in the groupIncludes NULLs
COUNT(col)Count non-NULL values in columnExcludes NULLs
COUNT(DISTINCT col)Count unique non-NULL valuesExcludes NULLs
SUM(col)Total of numeric columnIgnores NULLs
AVG(col)Mean of numeric columnIgnores NULLs (numerator AND denominator)
MIN(col) / MAX(col)Smallest / largest valueIgnores NULLs

2.2 GROUP BY and HAVING

SELECT  category,
        COUNT(*) AS order_count,
        SUM(amount) AS total_revenue,
        AVG(amount) AS avg_order_value,
        MAX(amount) AS highest_order
FROM    orders
WHERE   order_date >= '2024-01-01'    -- filter rows BEFORE grouping
GROUP BY category
HAVING  COUNT(*) > 50              -- filter groups AFTER aggregation
ORDER BY total_revenue DESC;
WHERE vs HAVING

WHERE filters individual rows before grouping. HAVING filters groups after aggregation. You cannot use aggregate functions (SUM, COUNT, etc.) in a WHERE clause — use HAVING instead. You can reference column aliases in ORDER BY but not in WHERE or HAVING in most databases.

Worked Example

Find the top 3 cities by total sales, but only include cities with more than 100 orders in the last year:

SELECT  city,
        COUNT(*) AS total_orders,
        SUM(amount) AS total_sales
FROM    orders
WHERE   order_date >= DATE_SUB(CURDATE(), INTERVAL 1 YEAR)
GROUP BY city
HAVING  COUNT(*) > 100
ORDER BY total_sales DESC
LIMIT   3;

3. Joins — All Types with Examples

Joins combine rows from two or more tables based on a related column. The type of join determines what happens to rows that don't have a match in the other table.

For all examples below, assume two tables:

customers

INNER JOIN

Returns only rows where the join condition is satisfied in BOTH tables. Rows with no match in either table are excluded.

Alice: 2 orders
Bob: 1 order
Carol: ✗ excluded

LEFT JOIN (LEFT OUTER)

Returns all rows from the LEFT table, plus matching rows from the right table. Non-matching right-side values appear as NULL.

Alice: 2 orders
Bob: 1 order
Carol: NULL (kept)

RIGHT JOIN (RIGHT OUTER)

Returns all rows from the RIGHT table, plus matching rows from the left table. Non-matching left-side values appear as NULL.

All orders kept
Left NULLs for unmatched customers

FULL OUTER JOIN

Returns all rows from both tables. Non-matching rows from either side appear with NULLs for the other side's columns.

All customers + all orders
NULLs where no match exists on either side

CROSS JOIN

Returns the Cartesian product of both tables — every row from the left paired with every row from the right. n×m rows total. Has no ON condition.

3 customers × 3 orders = 9 rows

SELF JOIN

A table joined to itself using aliases. Used for hierarchical data (employees and managers), comparing rows within the same table.

e.g., employee e1 JOIN employee e2 ON e1.manager_id = e2.id
-- INNER JOIN: customers who placed at least one order
SELECT  c.name, o.amount
FROM    customers c
INNER JOIN orders o ON c.id = o.customer_id;

-- LEFT JOIN: all customers, with NULL amount if no orders
SELECT  c.name, COALESCE(o.amount, 0) AS amount
FROM    customers c
LEFT JOIN orders o ON c.id = o.customer_id;

-- Find customers with NO orders (LEFT JOIN anti-pattern)
SELECT  c.name
FROM    customers c
LEFT JOIN orders o ON c.id = o.customer_id
WHERE   o.id IS NULL;

-- SELF JOIN: employee with their manager's name
SELECT  e.name AS employee,
        m.name AS manager
FROM    employees e
LEFT JOIN employees m ON e.manager_id = m.id;

4. Subqueries & CTEs

4.1 Subqueries

A subquery is a SELECT statement nested inside another SQL statement. It can appear in the SELECT, FROM, WHERE, or HAVING clause.

-- WHERE subquery: customers who spent above average
SELECT  customer_id, SUM(amount) AS total
FROM    orders
GROUP BY customer_id
HAVING  SUM(amount) > (
    SELECT AVG(total_spent)
    FROM (
        SELECT customer_id, SUM(amount) AS total_spent
        FROM orders
        GROUP BY customer_id
    ) AS customer_totals
);

-- FROM subquery (derived table)
SELECT  category, AVG(monthly_revenue) AS avg_monthly
FROM (
    SELECT category,
           DATE_FORMAT(order_date, '%Y-%m') AS month,
           SUM(amount) AS monthly_revenue
    FROM  orders
    GROUP BY category, month
) sub
GROUP BY category;

4.2 CTEs (Common Table Expressions)

A CTE defines a named, temporary result set using the WITH clause. It is executed once, can be referenced multiple times in the main query, and makes complex queries far more readable than nested subqueries.

-- CTE: monthly cohort retention
WITH first_orders AS (
    SELECT  customer_id,
            MIN(order_date) AS first_order_date,
            DATE_FORMAT(MIN(order_date), '%Y-%m') AS cohort_month
    FROM    orders
    GROUP BY customer_id
),
repeat_orders AS (
    SELECT  o.customer_id,
            f.cohort_month,
            TIMESTAMPDIFF(MONTH, f.first_order_date, o.order_date) AS months_since_first
    FROM    orders o
    JOIN    first_orders f ON o.customer_id = f.customer_id
    WHERE   o.order_date > f.first_order_date
)
SELECT  cohort_month,
        months_since_first,
        COUNT(DISTINCT customer_id) AS retained_customers
FROM    repeat_orders
GROUP BY cohort_month, months_since_first
ORDER BY cohort_month, months_since_first;
CTE vs Subquery

Prefer CTEs over deeply nested subqueries. CTEs are read top-to-bottom, can be referenced multiple times without re-executing, are debuggable step-by-step, and dramatically improve maintainability. In most databases, CTEs and subqueries produce identical execution plans, so the choice is about readability, not performance.

5. Window Functions

Definition

A window function performs a calculation across a set of rows (the "window") that are related to the current row — without collapsing those rows into a single output row. This is the key difference from GROUP BY: every row retains its identity in the output while still having access to aggregate information from its window.

5.1 Syntax

function_name([expression])
  OVER (
    [PARTITION BY column1, column2]    -- reset the window per partition
    [ORDER BY    column3 ASC|DESC]   -- define ordering within the window
    [ROWS|RANGE BETWEEN ... AND ...]  -- define the window frame
  )

5.2 Ranking Functions

SELECT
    employee_id,
    department,
    salary,
    ROW_NUMBER() OVER (PARTITION BY department ORDER BY salary DESC) AS row_num,
    RANK()       OVER (PARTITION BY department ORDER BY salary DESC) AS rnk,
    DENSE_RANK() OVER (PARTITION BY department ORDER BY salary DESC) AS dense_rnk,
    NTILE(4)     OVER (PARTITION BY department ORDER BY salary DESC) AS quartile
FROM employees;
FunctionTies handled howGap after ties?
ROW_NUMBER()Arbitrary ordering — no two rows share a numberN/A
RANK()Tied rows share the same rankYes (1,1,3 not 1,1,2)
DENSE_RANK()Tied rows share the same rankNo (1,1,2 not 1,1,3)
NTILE(n)Divides rows into n buckets as evenly as possibleN/A

5.3 Offset Functions: LAG and LEAD

SELECT
    order_date,
    revenue,
    LAG(revenue, 1) OVER (ORDER BY order_date) AS prev_day_revenue,
    LEAD(revenue, 1) OVER (ORDER BY order_date) AS next_day_revenue,
    revenue - LAG(revenue, 1) OVER (ORDER BY order_date) AS day_over_day_change,
    ROUND(
        (revenue - LAG(revenue, 1) OVER (ORDER BY order_date))
        / NULLIF(LAG(revenue, 1) OVER (ORDER BY order_date), 0) * 100, 2
    ) AS pct_change
FROM    daily_revenue
ORDER BY order_date;

5.4 Aggregate Window Functions & Running Totals

SELECT
    order_date,
    amount,
    SUM(amount) OVER (ORDER BY order_date) AS running_total,
    AVG(amount) OVER (
        ORDER BY order_date
        ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
    ) AS rolling_7day_avg,
    SUM(amount) OVER (PARTITION BY DATE_FORMAT(order_date, '%Y-%m')) AS monthly_total,
    amount / SUM(amount) OVER () * 100 AS pct_of_grand_total
FROM    orders
ORDER BY order_date;

6.4 Conditional Logic: CASE WHEN

SELECT
    order_id,
    amount,
    CASE
        WHEN amount < 500  THEN 'Low'
        WHEN amount < 2000 THEN 'Medium'
        ELSE                     'High'
    END AS order_tier,
    SUM(CASE WHEN status = 'returned' THEN 1 ELSE 0 END) AS return_count
FROM    orders
GROUP BY order_tier;

7. Query Optimization & Indexes

7.1 Indexes

Definition

An index is a data structure (typically a B-tree) that the database engine maintains alongside a table to allow fast row lookup without scanning every row. An index on column email means a query with WHERE email = 'x@y.com' can locate the row in O(log n) time instead of O(n) time.

  • Primary key index: Automatically created on the primary key column(s). Unique, not null.
  • Unique index: Enforces uniqueness of values in a column (e.g., email address).
  • Composite index: Index on multiple columns. Column order matters — the index is used for queries that filter on the leftmost prefix of the columns.
  • Full-text index: Optimizes LIKE/text search queries.
Index Trade-offs

Indexes speed up SELECT queries (fewer rows scanned) but slow down INSERT, UPDATE, and DELETE operations (the index must be updated with every write). Heavy indexing on write-intensive tables can be counterproductive. A practical rule: index columns that appear frequently in WHERE clauses, JOIN conditions, and ORDER BY clauses for large tables.

7.2 Optimization Principles

  • Avoid SELECT *: Fetch only needed columns. SELECT * reads all columns into memory even if the query only uses two.
  • Filter early: Apply WHERE conditions as early as possible to reduce the number of rows that subsequent operations must process.
  • Avoid functions on indexed columns in WHERE: WHERE YEAR(created_at) = 2024 prevents the engine from using an index on created_at. Rewrite as WHERE created_at BETWEEN '2024-01-01' AND '2024-12-31'.
  • Use EXPLAIN: Prefix a query with EXPLAIN to see the query execution plan — which indexes are used, the join type, estimated rows scanned. This is the standard tool for diagnosing slow queries.
  • Limit join complexity: Every additional join multiplies the row space the engine must traverse. Ensure join columns are indexed on both sides.
-- See the execution plan for any query
EXPLAIN SELECT customer_id, SUM(amount)
FROM   orders
WHERE  created_at BETWEEN '2024-01-01' AND '2024-12-31'
GROUP BY customer_id;

8. Solved Interview Problems

All problems use three tables. Schema:

-- Table: users
users(user_id INT PK, name VARCHAR, signup_date DATE, country VARCHAR)

-- Table: orders
orders(order_id INT PK, user_id INT FK, amount DECIMAL, order_date DATE, status VARCHAR)

-- Table: products
products(product_id INT PK, order_id INT FK, category VARCHAR, qty INT, unit_price DECIMAL)

1Find the total revenue and number of orders per country. Easy

SELECT  u.country,
        COUNT(o.order_id)    AS total_orders,
        SUM(o.amount)        AS total_revenue,
        AVG(o.amount)        AS avg_order_value
FROM    users u
JOIN    orders o ON u.user_id = o.user_id
WHERE   o.status = 'completed'
GROUP BY u.country
ORDER BY total_revenue DESC;

2Find users who have never placed an order. Easy

-- Method 1: LEFT JOIN anti-join
SELECT  u.user_id, u.name
FROM    users u
LEFT JOIN orders o ON u.user_id = o.user_id
WHERE   o.order_id IS NULL;

-- Method 2: NOT EXISTS (often more readable)
SELECT  user_id, name
FROM    users u
WHERE NOT EXISTS (
    SELECT 1 FROM orders o WHERE o.user_id = u.user_id
);

3Find the second highest order amount. Easy

-- Method 1: OFFSET (clean, modern)
SELECT  DISTINCT amount
FROM    orders
ORDER BY amount DESC
LIMIT   1 OFFSET 1;

-- Method 2: Subquery (works everywhere)
SELECT  MAX(amount) AS second_highest
FROM    orders
WHERE   amount < (SELECT MAX(amount) FROM orders);

4Rank users by total spending within each country. Medium

WITH user_spending AS (
    SELECT  u.user_id, u.name, u.country, SUM(o.amount) AS total_spent
    FROM    users u
    JOIN    orders o ON u.user_id = o.user_id
    WHERE   o.status = 'completed'
    GROUP BY u.user_id, u.name, u.country
)
SELECT  user_id, name, country, total_spent,
        DENSE_RANK() OVER (PARTITION BY country ORDER BY total_spent DESC) AS country_rank
FROM    user_spending
ORDER BY country, country_rank;

5Calculate month-over-month revenue growth percentage. Medium

WITH monthly_rev AS (
    SELECT  DATE_FORMAT(order_date, '%Y-%m') AS month,
            SUM(amount) AS revenue
    FROM    orders
    WHERE   status = 'completed'
    GROUP BY month
)
SELECT  month,
        revenue,
        LAG(revenue) OVER (ORDER BY month) AS prev_month_revenue,
        ROUND(
            (revenue - LAG(revenue) OVER (ORDER BY month))
            / NULLIF(LAG(revenue) OVER (ORDER BY month), 0) * 100, 2
        ) AS mom_growth_pct
FROM    monthly_rev
ORDER BY month;

6Find users who placed orders in both January and February 2024. Medium

SELECT  user_id
FROM    orders
WHERE   order_date BETWEEN '2024-01-01' AND '2024-02-29'
GROUP BY user_id
HAVING
    COUNT(DISTINCT MONTH(order_date)) = 2
    AND MIN(MONTH(order_date)) = 1
    AND MAX(MONTH(order_date)) = 2;

7Find the running total of orders per user, ordered by date. Medium

SELECT  user_id,
        order_date,
        amount,
        SUM(amount) OVER (
            PARTITION BY user_id
            ORDER BY     order_date
            ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
        ) AS cumulative_spend
FROM    orders
WHERE   status = 'completed'
ORDER BY user_id, order_date;

8Find the top-selling category per country. Medium

WITH category_sales AS (
    SELECT  u.country,
            p.category,
            SUM(p.qty * p.unit_price) AS revenue
    FROM    users u
    JOIN    orders o  ON u.user_id  = o.user_id
    JOIN    products p ON o.order_id = p.order_id
    WHERE   o.status = 'completed'
    GROUP BY u.country, p.category
),
ranked AS (
    SELECT  *,
            RANK() OVER (PARTITION BY country ORDER BY revenue DESC) AS rnk
    FROM    category_sales
)
SELECT  country, category, revenue
FROM    ranked
WHERE   rnk = 1
ORDER BY country;

9Find users whose total spend increased month-over-month for at least 3 consecutive months. Hard

WITH monthly AS (
    SELECT  user_id,
            DATE_FORMAT(order_date, '%Y-%m') AS month,
            SUM(amount) AS monthly_spend
    FROM    orders WHERE status = 'completed'
    GROUP BY user_id, month
),
with_prev AS (
    SELECT  user_id, month, monthly_spend,
            LAG(monthly_spend) OVER (PARTITION BY user_id ORDER BY month) AS prev_spend,
            LAG(month)         OVER (PARTITION BY user_id ORDER BY month) AS prev_month
    FROM    monthly
),
flags AS (
    SELECT  user_id, month,
            CASE WHEN monthly_spend > prev_spend
                      AND TIMESTAMPDIFF(MONTH, prev_month, month) = 1
                 THEN 1 ELSE 0 END AS increased
    FROM    with_prev
),
streaks AS (
    SELECT  user_id,
            SUM(increased) OVER (
                PARTITION BY user_id
                ORDER BY month
                ROWS BETWEEN 2 PRECEDING AND CURRENT ROW
            ) AS streak_3
    FROM    flags
)
SELECT DISTINCT user_id
FROM    streaks
WHERE   streak_3 = 3;

10Compute a 7-day rolling average of daily order count. Medium

WITH daily AS (
    SELECT  order_date, COUNT(*) AS daily_orders
    FROM    orders
    GROUP BY order_date
)
SELECT  order_date,
        daily_orders,
        AVG(daily_orders) OVER (
            ORDER BY order_date
            ROWS BETWEEN 6 PRECEDING AND CURRENT ROW
        ) AS rolling_7d_avg
FROM    daily
ORDER BY order_date;

SQL Concept Questions

SQL — Conceptual Q&A
QWhat is the difference between WHERE and HAVING?
WHERE filters rows before any grouping occurs (step 2 in SQL execution order). It operates on individual rows and cannot reference aggregate functions because aggregations have not yet been computed.

HAVING filters groups after GROUP BY has been applied (step 4). It can reference aggregate functions because it runs after they have been computed.

A practical rule: if the filter references an aggregation (SUM, COUNT, AVG, etc.), use HAVING. If it filters raw column values on individual rows, use WHERE. Both can appear in the same query — WHERE reduces the row set before grouping, HAVING reduces the group set after.
QWhat is the difference between RANK(), DENSE_RANK(), and ROW_NUMBER()?
All three assign integers to rows based on a specified ordering within a partition. The difference is how they handle ties:

ROW_NUMBER(): Assigns a unique sequential integer to every row. Ties are broken arbitrarily — no two rows share a number. Result for scores [90,90,85]: 1,2,3.

RANK(): Tied rows receive the same rank. After ties, the next rank is incremented by the number of tied rows (creating gaps). Result for [90,90,85]: 1,1,3 (rank 2 is skipped).

DENSE_RANK(): Tied rows receive the same rank. After ties, the next rank is n+1 with no gaps. Result for [90,90,85]: 1,1,2.

Use ROW_NUMBER to deduplicate or paginate. Use RANK/DENSE_RANK for leaderboards. Use DENSE_RANK when you want ranks that consumers can interpret as "Nth place" without gaps.
QWhat is a CTE and when would you use it instead of a subquery?
A CTE (Common Table Expression) is a named temporary result set defined with the WITH clause, available only for the duration of the query. It is logically equivalent to a derived table (FROM subquery) in most cases.

Prefer a CTE when:
  • The same derived result needs to be referenced more than once in the main query (write it once as a CTE, reference it multiple times).
  • The query has multiple sequential transformation steps — CTEs read top-to-bottom and are far easier to debug and maintain than deeply nested subqueries.
  • You want to build a query incrementally and verify each step.
Prefer a subquery when: the derived result is simple and used only once, and inlining it keeps the query compact.
QWhat is the difference between INNER JOIN and LEFT JOIN? When do you choose each?
INNER JOIN returns only rows where the join condition is satisfied in both tables. Rows from either table that have no matching row in the other are excluded from the result.

LEFT JOIN returns all rows from the left (first) table, and matching rows from the right table. If a left-table row has no match in the right table, right-table columns appear as NULL. The left table's row count is preserved.

Choose INNER JOIN when you only want records that exist in both tables — e.g., orders with their associated product details (orphaned orders are not meaningful).

Choose LEFT JOIN when you want all records from one table regardless of whether they have a match — e.g., all customers including those who have never ordered. The pattern LEFT JOIN … WHERE right.id IS NULL is the standard "anti-join" — finding rows with NO match.
QHow do window functions differ from GROUP BY?
GROUP BY collapses multiple rows into one row per group. After GROUP BY, individual row details are lost — you can only see the aggregated values.

Window functions compute aggregate values across related rows but keep every individual row in the output. The result set has the same number of rows as the input — each row gets an additional computed column (e.g., a running total, a rank, or the previous row's value).

Example: to see each order alongside the customer's total spending, GROUP BY would collapse to one row per customer (losing individual order details). A window function keeps every order row and adds a SUM(amount) OVER (PARTITION BY user_id) column — each order row shows both its own amount and the user's total.
