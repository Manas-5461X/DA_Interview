1. Why A/B Testing? Correlation vs. Causation

Observational analysis can identify correlations, but it cannot establish causality. Without a controlled experiment, confounders — variables that affect both the treatment assignment and the outcome — make it impossible to attribute an effect to a specific change.

Motivating Example

An analyst observes that users who use the mobile app's dark mode have 40% higher retention than light mode users. Can we conclude that enabling dark mode increases retention?

No. Dark mode users are a self-selected group — they are likely more engaged, tech-savvy, or power users to begin with. The higher retention may be entirely due to these pre-existing differences (confounders), not the dark mode feature itself. If we roll out forced dark mode to all users, retention may not change at all.

Only a randomized controlled experiment — randomly assigning some users to dark mode and others to light mode — allows us to attribute any difference in retention to the treatment (dark mode), because randomization balances all confounders (both observed and unobserved) between groups.

Definition

An A/B Test (also called a randomized controlled trial or split test) is an experiment in which users are randomly assigned to one of two or more groups: the control group (A, the current experience) and the treatment group (B, the new experience). The difference in outcomes between groups is measured and subjected to statistical hypothesis testing to determine whether the effect is real or could be due to chance.

2. The A/B Testing Framework

1

Define the Hypothesis

State a clear, falsifiable hypothesis before the experiment. "Changing the checkout button from blue to green will increase the purchase conversion rate." Define the null (H₀: no effect) and alternative (H₁: there is an effect).

2

Define the Primary Metric

Choose ONE primary metric (the OEC — Overall Evaluation Criterion). Be specific: not "engagement" but "7-day purchase rate per user". Also define guardrail metrics — secondary metrics that should not regress (e.g., page load time, error rate).

3

Define Significance Level (α) and Power (1−β)

Choose α (typical: 0.05) and power (typical: 0.8 or 0.9) before running the experiment. These drive the sample size calculation.

4

Calculate Required Sample Size

Use baseline rate, minimum detectable effect (MDE), α, and power to determine how many users per group are needed. Run the experiment for at least this duration.

5

Randomize & Run the Experiment

Randomly assign users to control or treatment. Check SRM (Sample Ratio Mismatch) immediately — the ratio of users in each group should match the intended split. Collect data for the full planned duration.

6

Analyze Results

Run the appropriate statistical test. Report: effect size (absolute and relative lift), p-value, and confidence interval. Do NOT just report "statistically significant" — report the magnitude.

7

Decide & Document

Make a ship/no-ship decision based on statistical significance AND practical significance (is the effect large enough to matter?). Document the experiment, its results, and the decision rationale for institutional knowledge.

3. Hypothesis Testing in A/B Tests

Null and Alternative Hypotheses

HypothesisSymbolStatement
Null HypothesisH₀There is no difference between control and treatment. Any observed difference is due to random chance. H₀: μ_treatment = μ_control (or p_treatment = p_control)
Alternative HypothesisH₁There is a real difference. H₁: μ_treatment ≠ μ_control (two-tailed) or μ_treatment > μ_control (one-tailed)

The Four Decision Outcomes

H₀ is True (No Real Effect)H₁ is True (Real Effect Exists)
Reject H₀ Type I Error (α)
False Positive. We conclude there is an effect when there is none. Rate = α (significance level)		 Correct Detection ✓
True Positive. Power = 1−β. We correctly detect a real effect.
Fail to Reject H₀ Correct Retention ✓
True Negative. Correctly conclude no effect.		 Type II Error (β)
False Negative. We miss a real effect. Rate = β. Power = 1−β.

Key Concepts

P-Value

The p-value is the probability of observing a test statistic as extreme as (or more extreme than) the one calculated, assuming the null hypothesis is true. A small p-value (e.g., p < 0.05) means the observed data would be very unlikely if there were no real effect. It does NOT mean there is a 95% probability that your hypothesis is correct.

Significance Level (α)

The significance level α is the pre-specified threshold for rejecting the null hypothesis. α = 0.05 means: if the null hypothesis is true, we accept a 5% probability of incorrectly rejecting it (Type I error rate). α must be chosen BEFORE seeing the data — changing it after looking at results is p-hacking.

Statistical Power (1−β)

Power is the probability that the test correctly detects a real effect of a given size. Power = 1 − β, where β is the Type II error rate. Conventionally, power = 0.8 (80%) is the minimum — meaning a 20% chance of missing a real effect. Higher power requires larger sample size.

Effect Size (MDE)

The Minimum Detectable Effect (MDE) is the smallest effect size that the experiment is designed to detect with the given power and significance level. If you need to detect a 2% lift in conversion rate and you only have a small sample, you may lack the power to detect it.

One-Tailed vs Two-Tailed Tests

A two-tailed test tests whether the treatment differs from control in either direction (better or worse). Use this as the default — you want to detect regressions too, not just improvements. A one-tailed test tests only one direction (e.g., treatment > control). It has more power to detect effects in that direction, but it assumes you only care about improvements and are willing to ignore regressions. One-tailed tests are rarely appropriate in practice.

4. Statistical Power & Sample Size

Sample Size Formula for Proportions (Two-Sided)
n = (z_{α/2} + z_β)² × [p₁(1−p₁) + p₂(1−p₂)] / (p₁ − p₂)²

For standard α=0.05, power=0.80:
z_{α/2} = z_{0.025} = 1.96
z_β = z_{0.20} = 0.84
(z_{α/2} + z_β)² ≈ 7.85

Simplified (equal variance approximation):
n ≈ 16 × σ² / δ² (for means)
n ≈ 16 × p(1−p) / δ² (for proportions)
where δ = p₂ − p₁ (MDE)
Worked Example: E-Commerce Checkout

Setup: Current checkout conversion rate (control): p₁ = 5.0%. We want to detect an improvement to p₂ = 5.5% (MDE = 0.5 percentage points = 10% relative lift). α = 0.05, Power = 0.80.

Calculation:
n ≈ 16 × 0.05 × 0.95 / (0.005)²
n ≈ 16 × 0.0475 / 0.000025
n ≈ 30,400 users per group → ~60,800 total users needed.

Duration estimate: If you get 5,000 daily visitors and split 50/50, each group gets 2,500/day. Duration = 30,400 / 2,500 ≈ 12.2 days. Run for at least 2 full weeks (to capture weekly seasonality).

Insight: Smaller MDE = larger required sample size. If you want to detect a 0.1 percentage point lift, you would need ~100× more users.

from statsmodels.stats.power import NormalIndPower, TTestIndPower
from statsmodels.stats.proportion import proportion_effectsize
import scipy.stats as stats

# ── SAMPLE SIZE FOR PROPORTIONS ─────────────────────────
p_control   = 0.05   # baseline conversion rate
p_treatment = 0.055  # target conversion rate (MDE)
alpha       = 0.05
power       = 0.80

# Effect size (Cohen's h for proportions)
effect_size = proportion_effectsize(p_treatment, p_control)

analysis = NormalIndPower()
n_per_group = analysis.solve_power(
    effect_size=effect_size,
    alpha=alpha,
    power=power,
    alternative='two-sided'
)
print(f"Sample size per group: {n_per_group:.0f}")
print(f"Total: {2 * n_per_group:.0f}")

# ── SAMPLE SIZE FOR MEANS (continuous metric) ─────────────
baseline_mean = 120   # e.g., average order value in $
std_dev       = 45    # standard deviation of AOV
mde_absolute  = 5     # want to detect $5 lift

effect_size_d = mde_absolute / std_dev  # Cohen's d
t_analysis = TTestIndPower()
n_per_group_t = t_analysis.solve_power(
    effect_size=effect_size_d,
    alpha=alpha,
    power=power,
    alternative='two-sided'
)
print(f"Sample size per group (AOV): {n_per_group_t:.0f}")

# ── POWER GIVEN SAMPLE SIZE ────────────────────────────────
# If you only have n=5000 per group, what's your power?
achieved_power = t_analysis.solve_power(
    effect_size=effect_size_d,
    alpha=alpha,
    nobs1=5000,
    alternative='two-sided'
)
print(f"Power with n=5000 per group: {achieved_power:.3f}")

5. Choosing the Right Statistical Test

Metric TypeTestWhen to Use
Binary (conversion rate, click rate) Two-Proportion Z-Test Large samples (n > 30); comparing p₁ vs p₂
Binary with small samples Fisher's Exact Test Small cell counts; exact p-value
Continuous (average order value, revenue, time) Two-Sample t-Test (Welch) Normal or large samples; does not assume equal variance
Continuous with non-normal distribution Mann-Whitney U Test Ordinal or skewed continuous data; non-parametric
Multiple variants (>2 groups) ANOVA + post-hoc tests Compare 3+ groups; use Bonferroni or Tukey for pairwise
Count data / ratios Chi-Square Test Categorical outcomes; contingency tables

6. Running the Analysis in Python

import numpy as np
import pandas as pd
from scipy import stats

# === BINARY METRIC: CONVERSION RATE ===
# Observed data
n_control   = 12500
n_treatment = 12300
conv_control   = 625   # conversions in control
conv_treatment = 680   # conversions in treatment

p_ctrl  = conv_control   / n_control    # 0.0500 = 5.00%
p_treat = conv_treatment / n_treatment  # 0.0553 = 5.53%
abs_lift = p_treat - p_ctrl             # 0.0053 = 0.53 pp
rel_lift = abs_lift / p_ctrl            # 10.6% relative lift

print(f"Control rate:   {p_ctrl:.4f} ({p_ctrl*100:.2f}%)")
print(f"Treatment rate: {p_treat:.4f} ({p_treat*100:.2f}%)")
print(f"Absolute lift: +{abs_lift*100:.3f} pp")
print(f"Relative lift: +{rel_lift*100:.1f}%")

# Two-proportion Z-test
from statsmodels.stats.proportion import proportions_ztest
count = np.array([conv_treatment, conv_control])
nobs  = np.array([n_treatment, n_control])
z_stat, p_value = proportions_ztest(count, nobs, alternative='two-sided')
print(f"Z-statistic: {z_stat:.4f}")
print(f"P-value: {p_value:.4f}")
print(f"Statistically significant (α=0.05): {p_value < 0.05}")

# 95% Confidence Interval for the difference
p_pool = (conv_control + conv_treatment) / (n_control + n_treatment)
se_diff = np.sqrt(p_ctrl*(1-p_ctrl)/n_control + p_treat*(1-p_treat)/n_treatment)
ci_lower = abs_lift - 1.96 * se_diff
ci_upper = abs_lift + 1.96 * se_diff
print(f"95% CI for lift: [{ci_lower*100:.3f}%, {ci_upper*100:.3f}%]")

# === CONTINUOUS METRIC: AVERAGE ORDER VALUE ===
# Simulate data
np.random.seed(42)
aov_control   = np.random.lognormal(mean=4.5, sigma=0.8, size=5000)
aov_treatment = np.random.lognormal(mean=4.6, sigma=0.8, size=5000)

t_stat, p_val = stats.ttest_ind(aov_treatment, aov_control, equal_var=False)
print(f"Control AOV:   ${aov_control.mean():.2f}")
print(f"Treatment AOV: ${aov_treatment.mean():.2f}")
print(f"T-stat: {t_stat:.4f}, P-value: {p_val:.4f}")

# Mann-Whitney U (non-parametric, good for skewed revenue data)
u_stat, mw_p = stats.mannwhitneyu(aov_treatment, aov_control, alternative='two-sided')
print(f"Mann-Whitney p-value: {mw_p:.4f}")

# === SRM CHECK: SAMPLE RATIO MISMATCH ===
# Expected 50/50 split. If SRM detected, do not interpret results!
chi2, srm_p = stats.chisquare([n_control, n_treatment])
print(f"SRM p-value: {srm_p:.4f}")
if srm_p < 0.01:
    print("WARNING: Sample Ratio Mismatch detected! Investigate before analyzing.")
else:
    print("SRM check passed.")

7. Common Pitfalls & How to Avoid Them

🎯 P-Hacking (Multiple Testing Problem)

What it is: Running the test until p < 0.05 and then stopping, or testing many metrics/segments and reporting only the significant ones. With 20 independent tests at α=0.05, you expect one false positive even if no effect exists.

Fix: Pre-register the primary metric and test before running. Apply Bonferroni correction (α/k for k tests) or use FDR control (Benjamini-Hochberg) for multiple comparisons. For continuous monitoring, use sequential testing methods (SPRT, mSPRT) designed for this purpose.

⏱️ Peeking (Early Stopping)

What it is: Looking at results before the experiment reaches its planned sample size and stopping early if p < 0.05. This dramatically inflates the Type I error rate — if you peek 5 times, your actual α can be 15–20% instead of 5%.

Fix: Determine the sample size before the experiment. Do not analyze results until the experiment is complete. If real-time monitoring is needed, use sequential testing methods with proper alpha-spending functions (O'Brien-Fleming, Pocock boundaries).

🆕 Novelty Effect (Primacy vs Novelty)

What it is: Users behave differently simply because the experience is new (novelty effect) or conversely because they miss the familiar interface (primacy effect). Either can cause the treatment to show a temporary lift or dip that doesn't persist.

Fix: Run the experiment long enough (at least 2–4 weeks) for novelty effects to dissipate. Analyze separately for new vs. returning users. Look at whether the treatment effect is decreasing over time (novelty wearing off).

🔀 Network Effects & Interference (SUTVA Violation)

What it is: The Stable Unit Treatment Value Assumption (SUTVA) requires that a unit's outcome depends only on its own treatment, not others'. In social networks, marketplaces, or referral programs, treating one user affects others in their network.

Fix: Use cluster-based randomization (assign entire social graph clusters to the same group). For marketplace experiments, use time-based randomization or geographically isolated markets.

📊 Sample Ratio Mismatch (SRM)

What it is: The actual ratio of users in control vs. treatment differs significantly from the intended ratio (e.g., you target 50/50 but observe 52/48). This indicates a bug in the randomization or logging that introduces systematic bias.

Fix: Always run a chi-square test for SRM at the start of analysis. If SRM is detected (p < 0.01), do not interpret the results. Find and fix the underlying bug first.

📅 Seasonality & Timing

What it is: Running an experiment only on weekdays misses weekend behavior. Running during a holiday means effects cannot be generalized to normal periods. Running for only 1–2 days misses weekly cycles.

Fix: Run experiments for full weeks (at minimum 2 weeks). Avoid starting experiments during major holidays, sales events, or product launches. Use holdout groups to measure long-term effects.

📉 Underpowered Experiments

What it is: Running an experiment that is too small to detect the effect you care about. A "negative" result from an underpowered experiment is uninformative — it doesn't mean there's no effect, just that you couldn't detect it.

Fix: Always calculate sample size before running. A negative result from a properly powered experiment is informative; a negative result from an underpowered one is not.

🔀 Survivorship Bias in Analysis

What it is: Filtering users (e.g., "analyze only users who made at least one purchase") after randomization. Post-randomization filters make the groups non-comparable — the filter itself may be affected by the treatment.

Fix: Any filters must be pre-treatment (apply before the experiment starts) or use the intent-to-treat (ITT) analysis: keep all randomized users in their assigned group for the analysis, regardless of actual treatment exposure.

8. Simpson's Paradox

Definition

Simpson's Paradox occurs when a trend present in several different groups reverses or disappears when the groups are combined. It arises because of a lurking (confounding) variable that is unequally distributed between groups and affects the outcome.

Classic Example: University Admissions

Consider two departments at a university:

DepartmentMale Accept RateFemale Accept Rate
Engineering80/200 = 40%10/20 = 50%
Humanities20/100 = 20%80/300 = 27%
Overall Combined100/300 = 33%90/320 = 28%

Within every department, women have a higher acceptance rate. But overall, men appear to have a higher rate. The paradox arises because women disproportionately apply to the more competitive Humanities department (lower acceptance rate for both genders), while men disproportionately apply to the easier Engineering department. The department is the confounding variable.

A/B Testing Context

You run an A/B test on a checkout flow. Overall, the treatment converts at 4.5% vs. control at 5.0% — seems like a negative result. But when segmented:

  • Mobile users: Treatment 4.0%, Control 3.5% → Treatment wins
  • Desktop users: Treatment 7.0%, Control 6.0% → Treatment wins

The paradox: more treatment users are on mobile (which has lower baseline conversion), pulling down the aggregate. In reality, the treatment is better for both groups. Fix: segment your analysis and check for heterogeneous effects. Use regression to control for confounders.

9. Bayesian A/B Testing (Overview)

The frequentist (p-value) approach asks: "What is the probability of observing this data if there is no effect?" The Bayesian approach asks: "Given the data, what is the probability that treatment is better than control?"

PropertyFrequentist (p-value)Bayesian
InterpretationP(data | H₀) — probability of data under nullP(H₁ | data) — probability treatment is better given data
Prior knowledgeNot incorporatedIncorporated via prior distribution
Outputp-value + binary decision (reject/fail to reject)Posterior distribution; probability that B > A; expected loss
PeekingInvalidates results (inflates α)Valid to update continuously (with proper prior)
InterpretabilityCounterintuitive (p-value is often misunderstood)Direct: "There's 97% probability treatment is better"
When to useRegulated industries, standard practice, many stakeholders expect itFaster decisions needed, sequential monitoring, business analysts
 
import numpy as np
from scipy.stats import beta

# Bayesian A/B test for conversion rates
# Prior: Beta(1,1) = Uniform (uninformative prior)
# Posterior after data: Beta(alpha + successes, beta + failures)

alpha_prior = beta_prior = 1  # uninformative prior

# Control: 625 conversions out of 12500
alpha_ctrl = alpha_prior + 625
beta_ctrl  = beta_prior  + (12500 - 625)

# Treatment: 680 conversions out of 12300
alpha_treat = alpha_prior + 680
beta_treat  = beta_prior  + (12300 - 680)

# Monte Carlo: probability that treatment > control
n_samples = 100_000
ctrl_samples  = beta.rvs(alpha_ctrl, beta_ctrl, size=n_samples)
treat_samples = beta.rvs(alpha_treat, beta_treat, size=n_samples)

prob_treat_better = (treat_samples > ctrl_samples).mean()
expected_lift = (treat_samples - ctrl_samples).mean()

print(f"P(Treatment > Control): {prob_treat_better:.4f} ({prob_treat_better*100:.1f}%)")
print(f"Expected lift: {expected_lift*100:.3f}%")

# 95% credible interval for treatment rate
ci = beta.interval(0.95, alpha_treat, beta_treat)
print(f"Treatment 95% credible interval: [{ci[0]*100:.2f}%, {ci[1]*100:.2f}%]")

Interview Q&A

An A/B test shows p = 0.03. What does this mean, and can you conclude the treatment is better?

A p-value of 0.03 means: if the null hypothesis were true (no real difference between control and treatment), the probability of observing a test statistic as extreme as the one we observed is 3%. Since 0.03 < α = 0.05, we reject the null hypothesis.

Common misinterpretations to avoid:

  • It does NOT mean there is a 97% probability the treatment is better
  • It does NOT tell you the size of the effect — only that the effect is unlikely to be zero
  • It does NOT mean the result is practically significant — a 0.01% lift with p=0.03 is statistically significant but may be meaningless for business

What you should also report:

  • Effect size: what is the absolute and relative lift?
  • 95% confidence interval: what is the range of plausible effects?
  • Practical significance: is this lift large enough to justify the engineering cost and opportunity cost of launching?
  • Guardrail metrics: did any negative secondary effects emerge?
  • SRM check: was the sample ratio as expected?

A statistically significant result is necessary but not sufficient to ship a feature. You need both statistical and practical significance, plus confidence that no guardrail metrics were harmed.

You run an A/B test for 2 days and see a big positive effect. Should you ship it?

Almost certainly not — and there are several reasons to be very cautious:

1. Insufficient power: Your sample size was probably calculated for a longer duration. Stopping early means the test may be underpowered — the result may not be reproducible with more data.

2. Peeking / alpha inflation: If you ran the test planning to evaluate it at 2 days, that's fine. But if you looked after 2 days because it looked promising and the original plan was 2 weeks, you've peeked. The actual Type I error rate is much higher than α = 0.05.

3. Novelty effect: Users may behave differently simply because something is new. This effect typically dissipates within 1–2 weeks. A 2-day result may show a short-term spike that disappears completely after a week.

4. Weekly seasonality: 2 days doesn't capture the full weekly cycle of user behavior. Monday–Tuesday behavior is different from Friday–weekend. A proper test needs at least 1–2 full weeks.

What to do: Continue the experiment to the planned duration. If you genuinely cannot wait, use a sequential testing method (like SPRT) that accounts for continuous monitoring, but note that the result still needs to be validated over a proper time period before shipping.

What is the difference between statistical significance and practical significance?

Statistical significance asks: "Is this effect unlikely to be zero?" It is a function of the sample size, effect size, and variance. With a large enough sample, even a tiny, meaningless effect will be statistically significant. With a small sample, even a large effect may not be statistically significant.

Practical significance asks: "Is this effect large enough to matter for the business?" It is a function of the effect size relative to business constraints — cost, effort, user experience impact, and strategic priority.

Illustrative examples:

  • Statistical significance without practical significance: With 10M users, you detect a 0.001% increase in conversion. p < 0.001, but the revenue impact is negligible and the engineering cost exceeds the benefit. Don't ship.
  • Practical significance without statistical significance: A change appears to increase revenue by 15%, but you only have 500 users per group and p = 0.12. The effect size matters, but the test is underpowered. Don't ship yet — run longer to get a conclusive answer.

Good decision-making requires both. A useful framework: define the MDE (minimum effect you care about) before the experiment. If the observed effect exceeds the MDE AND is statistically significant, ship. If it's below the MDE, it may not be worth shipping even if statistically significant.

How do you handle an A/B test where the metric is highly skewed (e.g., revenue per user)?

Revenue per user is often extremely right-skewed: most users spend nothing, some spend a little, and a few high-value users spend a lot. This violates the normality assumption of the t-test and makes the variance estimate unstable.

Option 1: Non-parametric test (Mann-Whitney U). Does not assume normality. Tests whether treatment users tend to have higher values than control users. Appropriate for ordinal or heavily skewed data.

Option 2: Log transformation. If revenue is log-normally distributed, apply log(1+x) to normalize it, then run a t-test on the transformed data. Report the effect as a percentage change in geometric mean.

Option 3: Bootstrap confidence intervals. Non-parametric: resample your data with replacement 10,000 times, compute the mean difference each time, and use the empirical distribution to construct confidence intervals. No distributional assumptions.

Option 4: CUPED (Controlled-experiment Using Pre-Experiment Data). Reduce variance by using pre-experiment data (user revenue from the prior period) as a covariate. Adjust the metric: Y_adjusted = Y − θ × (X − E[X]), where X is the pre-experiment covariate. Reduces variance by 30–70%, dramatically improving power. Used extensively at Microsoft, LinkedIn.

Option 5: Separate the metric. Decompose revenue = conversion rate × revenue per purchaser. Run the test on conversion rate (a proportion, amenable to Z-test) and revenue per purchaser separately. You can combine the CIs to reason about total revenue impact.

Explain Simpson's Paradox with a real-world example relevant to product analytics.

Simpson's Paradox occurs when an aggregate trend reverses when the data is broken down by a confounding variable. In product analytics, it commonly appears in A/B tests or reporting when different user segments have very different baseline rates AND are unequally distributed between groups.

Product example: You launch a new onboarding flow (treatment) and measure 30-day retention. Overall: treatment 38%, control 42% — treatment appears worse. But:

  • New users (70% of treatment, 30% of control): treatment 35%, control 30% → treatment better
  • Returning users (30% of treatment, 70% of control): treatment 55%, control 50% → treatment better

The treatment was better for both segments, but the aggregate was misleading because the treatment group had more new users (who have lower baseline retention), which pulled down the aggregate number. The confounding variable is "user type."

Resolution:

  • Always segment your A/B test results by key user characteristics (new vs. returning, platform, region)
  • Check for SRM by segment to ensure randomization worked
  • Use regression-based analysis to control for confounders
  • Be suspicious of aggregate results that contradict every segment-level result
